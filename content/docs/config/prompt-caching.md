## 프롬프트 캐싱이 뭔가요?

> 🍱 **비유**: 도서관 사서에게 "1번부터 100번 선반 책 목록 알려줘"를 매번 물어보지 않고, 처음 한 번만 조사해 메모해두고 "이번엔 101번 선반만 새로 확인"하는 것처럼 — 이미 처리한 내용은 다시 처리하지 않아요.

Claude Code는 매 턴마다 API에 요청을 보내요. 이때 **이전 대화 전체**를 매번 다시 보내는데, 캐싱이 있으면 "변하지 않은 부분"은 재처리 없이 재사용해요. 덕분에 **응답이 빠르고 비용도 적어**요.

---

## 캐시 3계층 구조

캐시는 아래 순서로 쌓여요. **위에 있는 계층이 바뀌면 그 아래 것도 다 리셋**됩니다.

| 계층 | 내용 | 언제 바뀌나요? |
|---|---|---|
| 1️⃣ **시스템 프롬프트** | 핵심 지침, 툴 정의, 출력 스타일 | MCP 서버 연결/해제, Claude Code 업그레이드 |
| 2️⃣ **프로젝트 컨텍스트** | CLAUDE.md, 자동 메모리, 규칙 | 세션 시작, `/clear`, `/compact` 후 |
| 3️⃣ **대화** | 내 메시지, 클로드 답변, 툴 결과 | 매 턴 |

> 🍱 **비유**: 3단 케이크처럼 — 맨 아래 층(시스템 프롬프트)을 바꾸면 위의 모든 층이 무너지지만, 맨 위 층(대화)만 바꾸면 아래 두 층은 그대로예요.

---

## 캐시를 리셋하는 행동 5가지

이 행동들을 하면 **다음 턴이 느리고 비싸**게 됩니다. 리셋 후 첫 턴에 캐시를 새로 쌓고, 그 이후부터 다시 빨라져요.

### 1. 모델 바꾸기 (`/model`)

모델마다 별도 캐시예요. Sonnet에서 Opus로 바꾸면 같은 대화 내용이라도 처음부터 다시 처리해요.

```
> /model claude-opus-4-7   ← 이 시점에서 캐시 리셋!
```

<div class="note-star">
★ <strong>opusplan 설정 주의</strong> — <code>opusplan</code> 모델을 쓰면 Plan 모드 진입 시 Opus로, 나갈 때 Sonnet으로 모델이 바뀌어요. Plan 모드 토글할 때마다 캐시 리셋이 발생해요.
</div>

### 2. MCP 서버 연결 또는 해제

툴 정의는 시스템 프롬프트 계층에 들어가요. MCP 서버가 연결되거나 끊기면 툴 목록이 바뀌어 캐시가 리셋됩니다.

- 내가 직접 연결/해제하지 않아도 **서버 프로세스가 종료**되거나 **HTTP 세션이 만료**되면 자동으로 리셋돼요.
- MCP 설정 파일을 편집해도 **그 자체로는 리셋 없음** — 재시작할 때 반영돼요.

### 3. 툴 전체 거부 규칙 추가

`Bash` 또는 `WebFetch` 같이 **툴 이름만 적는 deny 규칙**은 툴 정의 자체를 클로드 컨텍스트에서 제거해요 → 캐시 리셋.

```json
// 이렇게 추가하면 캐시 리셋 (툴 전체 제거)
{ "denyTools": ["Bash"] }

// 이렇게 제한하면 캐시 유지 (스코프 규칙, 툴은 그대로)
{ "rules": [{ "permission": "deny", "tool": "Bash(rm *)" }] }
```

### 4. /compact (대화 압축)

`/compact`는 대화 이력을 요약으로 교체해요. 당연히 캐시가 리셋되지만, **요약을 생성하는 요청 자체는 기존 캐시를 활용**해서 처리 비용이 크지 않아요.

> 🍱 **비유**: 오랜 통화 내용을 "요약본"으로 교체하는 것처럼 — 요약 작성 자체는 빠르고, 이후 대화는 훨씬 가벼워요.

**팁**: 작업 중간이 아니라 **작업 사이 자연스러운 전환점에** `/compact`를 쓰면 캐시 리셋 타이밍을 조절할 수 있어요.

### 5. Claude Code 업그레이드

새 버전은 시스템 프롬프트나 툴 정의를 바꿔요. 업그레이드 후 첫 턴은 캐시 리셋이에요.

- 자동 업데이트는 **세션 중엔 적용 안 됨** — 다음 실행할 때 반영돼요.
- 오래된 세션을 resume하면 이전 대화 전체가 새 시스템 프롬프트와 맞지 않아 처음부터 다시 처리돼요.

## 캐시가 유지되는 행동들

이 행동들은 대화의 끝에 **추가**되거나 요청에 영향을 안 줘서 캐시가 안 깨져요.

| 행동 | 왜 캐시 유지? |
|---|---|
| 저장소 파일 편집 | 파일 내용은 클로드가 읽을 때 대화에 추가됨. 미리 알려주지 않음 |
| **CLAUDE.md 세션 중 편집** | 세션 시작 때 한 번 읽힌 후 메모리에 유지됨 |
| 출력 스타일 변경 (`/config`) | 시스템 프롬프트는 세션 시작 때 고정됨 |
| 권한 모드 변경 | 시스템 프롬프트/툴 정의를 건드리지 않음 |
| 스킬 · 명령어 호출 | 대화 끝에 추가되는 방식 |
| `/recap` | 요약을 화면에만 보여주고, 대화 이력은 안 건드림 |
| `/rewind` | 이전 캐시 지점으로 되감음 — 그 지점 이후만 리셋 |

<div class="note-star">
★ <strong>중요</strong> — CLAUDE.md를 세션 중에 편집해도 <strong>현재 세션엔 반영 안 돼요</strong>. <code>/clear</code>나 재시작 후에 적용됩니다. 이건 버그가 아니라 캐시 유지를 위한 의도된 동작이에요.
</div>

## 캐시 유지 시간 (TTL)

캐시는 일정 시간 동안 안 쓰이면 사라져요. 쓸 때마다 타이머가 리셋됩니다.

| 인증 방식 | 기본 TTL | 1시간 TTL 활성화 |
|---|---|---|
| Claude 구독 (Pro/Max 등) | **자동 1시간** | 기본 적용 |
| API 키 / Bedrock / Vertex | 5분 | `ENABLE_PROMPT_CACHING_1H=1` |

```bash
# API 키 사용 중에 1시간 캐시 켜기
export ENABLE_PROMPT_CACHING_1H=1

# 항상 5분 캐시 강제 (디버깅용)
export FORCE_PROMPT_CACHING_5M=1
```

> 🍱 **비유**: 도서관 메모가 5분 뒤에 사라지냐, 1시간 뒤에 사라지냐 차이예요. 긴 작업 중에 잠깐 자리 비웠다 돌아오면 캐시가 살아있을 수도 있고 없을 수도 있어요.

## 캐시 성능 확인하기

스테이터스라인을 설정하면 실시간으로 캐시 토큰을 볼 수 있어요.

| 지표 | 의미 |
|---|---|
| `cache_read_input_tokens` | 캐시에서 재사용한 토큰 (약 10% 과금) |
| `cache_creation_input_tokens` | 이번 턴에 새로 캐시에 쓴 토큰 (쓰기 요금) |

**read 비율이 높을수록 캐싱 효과가 좋아요**. creation이 계속 높다면 무언가가 캐시를 계속 리셋하고 있다는 신호예요.

---

## 캐싱 끄기 (디버깅용)

특정 상황에서 캐싱 동작을 확인하거나 문제를 찾을 때:

```bash
export DISABLE_PROMPT_CACHING=1          # 전체 비활성화
export DISABLE_PROMPT_CACHING_HAIKU=1    # Haiku만
export DISABLE_PROMPT_CACHING_SONNET=1   # Sonnet만
export DISABLE_PROMPT_CACHING_OPUS=1     # Opus만
```

일반적인 사용에서는 캐싱을 끌 필요 없어요.

## 실전 팁

- 🏃 **세션 시작할 때** 모델과 MCP 서버를 먼저 설정하세요 — 중간에 바꾸면 캐시가 리셋돼요.
- ✂️ **`/compact`는 작업 사이** 자연스러운 쉬는 타이밍에 — 한창 작업 중에 쓰면 속도 저하가 느껴져요.
- ⏪ 잘못된 방향으로 갔다면 `/compact` 대신 **`/rewind`** — 이전 캐시 지점으로 되돌아가서 더 가벼워요.
- ☕ **자리 비울 때**: API 키 사용자는 5분 후 캐시가 사라져요. Pro/Max 구독자는 1시간 여유가 있어요.
