## Git? GitHub? 도대체 뭔가요?

클로드 코드를 쓰다 보면 "커밋해줘", "푸시해줘", "PR 만들어줘" 같은 말이 나옵니다. 처음 들으면 외계어 같죠. 하지만 걱정 마세요. **이미 매일 하고 있는 것**들입니다.

> 💡 **한 줄 요약**: Git은 **문서 버전 관리 프로그램**, GitHub은 **그 문서를 보관하는 클라우드 창고**입니다.

---

## 비유로 시작하기: "요리 레시피북"

여러분이 요리 레시피를 정리한다고 상상해보세요.

### Git이 없을 때

```
김치찌개_레시피.docx
김치찌개_레시피_수정.docx
김치찌개_레시피_최종.docx
김치찌개_레시피_진짜최종.docx
김치찌개_레시피_이게마지막.docx   ← 우리 모두의 현실
```

어떤 게 진짜 최종인지 모르겠고, 2주 전에 뭘 바꿨는지 기억도 안 나죠.

### Git이 있을 때

```
김치찌개_레시피.docx

  📝 버전 5 (오늘): "고춧가루 양 2큰술로 수정"
  📝 버전 4 (어제): "멸치육수 → 다시다로 변경"
  📝 버전 3 (3일 전): "두부 넣는 순서 변경"
  📝 버전 2 (1주일 전): "돼지고기 추가"
  📝 버전 1 (최초): "기본 김치찌개"
```

파일은 하나인데, **언제 뭘 바꿨는지 전부 기록**됩니다. 실수했으면 이전 버전으로 돌아갈 수도 있고요.

**이게 Git입니다.** 파일의 변경 기록을 자동으로 관리해주는 프로그램.

---

## 핵심 용어 10개 — 일상 비유로 이해하기

### 1. 저장소 (Repository, "레포")

> **비유: 레시피 노트 한 권**

프로젝트 전체를 담는 폴더입니다. 레시피 노트 한 권에 재료, 만드는 법, 사진이 다 들어있듯이, 저장소 하나에 코드, 설정, 문서가 다 들어있습니다.

```
내-프로젝트/          ← 이게 저장소 (레포)
├── index.html
├── style.css
├── README.md
└── .git/            ← Git이 변경 기록을 보관하는 곳 (숨김 폴더)
```

---

### 2. 커밋 (Commit)

> **비유: Ctrl+S 저장 + 포스트잇 메모 붙이기**

한글이나 워드에서 Ctrl+S 누르면 저장되죠? 커밋은 거기에 **"오늘 뭘 바꿨는지 메모"**까지 붙이는 저장입니다. 나중에 "그때 그 버전으로 돌아가야지" 할 때, 메모를 보고 바로 찾을 수 있습니다.

```
저장 1: "홈페이지 뼈대 만듦"        ← 📌 메모 붙임
저장 2: "색깔이랑 글꼴 입힘"        ← 📌 메모 붙임
저장 3: "연락처 페이지 추가"        ← 📌 메모 붙임
저장 4: "뭔가 잘못됨 😱"           ← 여기서 실수!
         ↓
      저장 3으로 되돌리기!          ← 메모 보고 찾아서 복구!
```

클로드에게 이렇게 말하면 됩니다:

```
"지금까지 한 거 저장(커밋)해줘"
```

---

### 3. 푸시 (Push)

> **비유: 내 컴퓨터 파일을 구글 드라이브(클라우드)에 올리기**

커밋(저장)은 **내 컴퓨터에만** 남아있습니다. 이걸 인터넷 저장소(GitHub)에 올리는 게 푸시입니다. 카톡에서 사진을 찍으면 내 폰에만 있잖아요? 그걸 카톡 앨범에 **올리는 동작**이 푸시예요.

```
내 컴퓨터              GitHub (인터넷 저장소)
    📁 ──── push ────→     ☁️
         "올린다"
```

왜 필요하냐고요?
- 컴퓨터가 고장 나도 **백업**이 있으니 안전합니다
- 집 컴퓨터든, 회사 컴퓨터든 **어디서든 이어서** 작업할 수 있습니다

```
"깃허브에 올려줘(푸시해줘)"
```

---

### 4. 풀 (Pull)

> **비유: 클라우드에서 최신 파일 다시 내려받기**

푸시의 반대입니다. 인터넷 저장소에 있는 최신 버전을 내 컴퓨터로 가져오는 거예요. 카톡 앨범에서 사진을 **다운로드**하는 것과 같습니다.

```
내 컴퓨터              GitHub (인터넷 저장소)
    📁 ←── pull ──────     ☁️
         "내려받는다"
```

집에서 작업하고 푸시(올리기)해뒀다가, 카페에서 노트북 열어서 풀(내려받기)하면 이어서 작업할 수 있습니다.

---

### 5. 브랜치 (Branch)

> **비유: 원본은 놔두고 복사본에서 실험하기**

제안서를 완성해서 부장님께 보고했는데, "이 부분 다르게 해보면 어떨까?" 싶을 때 — 원본 파일은 건드리지 않고 **사본을 하나 만들어서 실험**하잖아요?

```
원본 제안서 (main) ─────────────────→ 승인된 버전, 안전하게 유지
         │
         └── 실험 버전 (B안) ────────→ 여기서 마음껏 수정
                    │
                    ├── 더 낫다! → 원본에 반영하기 ✅
                    └── 별로다… → 그냥 버리기 🗑️
```

이게 브랜치입니다. **원본을 건드리지 않고 안전하게 실험**하는 공간. 실험이 맘에 들면 원본에 합치고, 아니면 그냥 버리면 됩니다.

---

### 6. 머지 (Merge)

> **비유: 실험 결과가 좋으니 원본에 반영하기**

브랜치(실험 버전)에서 수정한 게 맘에 들면, 원본에 합칩니다. 이걸 머지라고 해요. 실험 제안서의 B안이 더 나아서 원본 제안서에 반영하는 거죠.

```
원본 (main):        제안서 v1
실험 (B안):         + 예산 절감안 추가
                        ↓ merge (합치기)
원본 (main):        제안서 v1 + 예산 절감안   ← 반영 완료!
```

---

### 7. PR (Pull Request, 풀 리퀘스트)

> **비유: 결재 올리기**

회사에서 기안서를 쓰면, 바로 시행하지 않고 **팀장님한테 결재를 올리잖아요?** PR이 딱 그겁니다. "제가 이렇게 수정했는데 반영해도 될까요?" 하고 검토를 요청하는 거예요.

```
나: "홈페이지 디자인 바꿨습니다. 확인 부탁드립니다!" (PR = 결재 올림)
        ↓
팀장: "좋은데, 글꼴만 좀 더 키워주세요" (리뷰 = 검토 의견)
        ↓
나: "수정했습니다!" (재수정)
        ↓
팀장: "좋아요, 반영하세요!" (승인 = 머지)
```

혼자 작업하면 결재 없이 바로 반영해도 됩니다. 하지만 PR을 쓰면 **"내가 뭘 바꿨는지" 기록이 깔끔하게 남아서** 나중에 추적하기 좋아요.

```
"PR 만들어줘"
```

클로드가 알아서 제목, 설명, 변경 내용 요약까지 작성해서 올려줍니다.

---

### 8. 클론 (Clone)

> **비유: 공유 폴더를 내 컴퓨터에 통째로 복사하기**

회사 공유 드라이브에 있는 프로젝트 폴더를 **내 컴퓨터에 그대로 복사**해오는 것입니다. 파일뿐 아니라 **그동안의 수정 이력까지 전부** 따라옵니다.

```bash
git clone https://github.com/회사/프로젝트.git
```

이러면 `프로젝트` 폴더가 내 컴퓨터에 생기고, 이후부터는 자유롭게 수정할 수 있습니다.

---

### 9. 스테이징 (Staging, "Add")

> **비유: 서류 봉투에 넣을 문서 고르기**

여러 문서를 수정했는데, 이번에 **전부 다 제출할 건 아니잖아요?** 제출할 문서만 골라서 봉투에 넣는 과정이 스테이징입니다.

```
수정된 파일들:
  ✏️ 제안서.docx      ← 이건 제출 (봉투에 넣음)
  ✏️ 예산표.xlsx      ← 이것도 제출 (봉투에 넣음)
  ✏️ 메모.txt         ← 이건 아직 (내 참고용)

git add 제안서.docx 예산표.xlsx   ← 봉투에 담기 (스테이징)
git commit                        ← 제출! (커밋)
```

클로드가 커밋할 때 알아서 필요한 파일만 골라서 담아줍니다. 직접 고를 필요 없어요.

---

### 10. 충돌 (Conflict)

> **비유: 같은 곳을 두 명이 다르게 고쳐서 꼬인 것**

Git이 "여기 두 군데서 다르게 수정됐는데, 어느 쪽을 쓸까요?" 하고 물어보는 상황입니다. 클로드에게 "충돌 해결해줘"라고 하면 알아서 정리해줍니다.

---

## 전체 흐름 — 한 장으로 보기

```
① 작업하기
   파일을 수정하거나 새로 만듭니다
        ↓
② 스테이징 (add)
   "이 파일들을 저장할 거야" 골라서 담습니다
        ↓
③ 커밋 (commit)
   "지금 상태를 저장!" + 메모를 남깁니다
        ↓
④ 푸시 (push)
   인터넷 저장소(GitHub)에 올립니다
        ↓
⑤ (팀 작업 시) PR 생성
   "이렇게 수정했는데 반영해도 될까요?" 결재를 올립니다
        ↓
⑥ 머지 (merge)
   승인되면 원본에 반영합니다
```

## 클로드 코드에서는 이 모든 게 쉬워집니다

Git 명령어를 외울 필요가 없습니다. 한국어로 말하면 클로드가 알아서 합니다.

| 하고 싶은 것 | 클로드에게 이렇게 말하세요 |
|------------|----------------------|
| 저장하고 싶다 | "지금까지 한 거 커밋해줘" |
| 인터넷에 올리고 싶다 | "깃허브에 푸시해줘" |
| 최신 버전 받고 싶다 | "풀 받아줘" |
| 실험용 사본 만들고 싶다 | "새 브랜치 만들어줘" |
| 실험 결과를 원본에 반영하고 싶다 | "main에 머지해줘" |
| 검토(결재) 요청하고 싶다 | "PR 만들어줘" |
| 뭐가 바뀌었는지 보고 싶다 | "변경사항 보여줘" |
| 이전 버전으로 돌리고 싶다 | "마지막 커밋 전으로 돌려줘" |
| 프로젝트 복사해오고 싶다 | "이 레포 클론해줘" |

> **핵심**: Git은 도구일 뿐이고, **클로드가 대신 다뤄줍니다.** 여러분은 "뭘 하고 싶은지"만 말하면 됩니다.

## GitHub은 뭐가 다른 건가요?

혼동하기 쉬운데, **Git ≠ GitHub**입니다.

| | Git | GitHub |
|---|---|---|
| **한마디로** | 내 컴퓨터에서 돌아가는 **기록 도구** | 그 기록을 인터넷에 올려두는 **저장소** |
| **역할** | 파일이 언제, 어떻게 바뀌었는지 추적 | 추적한 기록을 클라우드에 보관·공유 |
| **비용** | 무료 | 무료 (유료 기능 있음) |
| **필수?** | 버전 관리 자체는 Git만으로 가능 | 백업, 다른 PC 동기화, 배포하려면 필요 |

쉽게 말해, **Git이 기록하고 GitHub이 보관합니다.** 둘이 세트로 쓰는 거예요.

## 자주 나오는 질문

### "나는 개발자가 아닌데 Git을 왜 알아야 해요?"

클로드 코드로 웹사이트를 만들거나, 자동화 스크립트를 짜면 그 결과물이 **파일**로 생깁니다. Git은 그 파일들을 안전하게 관리하고, 실수해도 되돌릴 수 있게 해주는 **안전망**입니다.

### "GitHub 계정이 꼭 필요한가요?"

로컬에서 Git만 써도 버전 관리는 됩니다. 하지만 **백업, 다른 PC 동기화, Vercel 배포** 등을 하려면 GitHub 계정이 필요합니다. 무료로 만들 수 있어요.

### "실수로 중요한 파일을 지워도 복구되나요?"

커밋해둔 상태라면 **언제든 복구**할 수 있습니다. 그래서 자주 커밋(저장)하는 습관이 중요합니다. 문서 작업할 때 Ctrl+S를 자주 누르는 것과 똑같은 이치예요.

### "private 저장소는 남들이 못 보나요?"

네. private(비공개) 저장소는 **나만** 볼 수 있습니다. 공개하고 싶은 프로젝트만 public으로 만들면 됩니다.
