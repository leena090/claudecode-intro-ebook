## Git? GitHub? 도대체 뭔가요?

클로드 코드를 쓰다 보면 "커밋해줘", "푸시해줘", "PR 만들어줘" 같은 말이 나옵니다. 처음 들으면 외계어 같죠. 하지만 걱정 마세요. **이미 매일 하고 있는 것**들입니다.

> 💡 **한 줄 요약**: Git은 **문서 버전 관리 프로그램**, GitHub은 **그 문서를 보관하는 클라우드 창고**입니다.

---

## 비유로 시작하기: "요리 레시피북"

여러분이 요리 레시피를 정리한다고 상상해보세요.

### Git이 없을 때

```
김치찌개_레시피.docx
김치찌개_레시피_수정.docx
김치찌개_레시피_최종.docx
김치찌개_레시피_진짜최종.docx
김치찌개_레시피_이게마지막.docx   ← 우리 모두의 현실
```

어떤 게 진짜 최종인지 모르겠고, 2주 전에 뭘 바꿨는지 기억도 안 나죠.

### Git이 있을 때

```
김치찌개_레시피.docx

  📝 버전 5 (오늘): "고춧가루 양 2큰술로 수정"
  📝 버전 4 (어제): "멸치육수 → 다시다로 변경"
  📝 버전 3 (3일 전): "두부 넣는 순서 변경"
  📝 버전 2 (1주일 전): "돼지고기 추가"
  📝 버전 1 (최초): "기본 김치찌개"
```

파일은 하나인데, **언제 뭘 바꿨는지 전부 기록**됩니다. 실수했으면 이전 버전으로 돌아갈 수도 있고요.

**이게 Git입니다.** 파일의 변경 기록을 자동으로 관리해주는 프로그램.

---

## 핵심 용어 10개 — 일상 비유로 이해하기

### 1. 저장소 (Repository, "레포")

> **비유: 레시피 노트 한 권**

프로젝트 전체를 담는 폴더입니다. 레시피 노트 한 권에 재료, 만드는 법, 사진이 다 들어있듯이, 저장소 하나에 코드, 설정, 문서가 다 들어있습니다.

```
내-프로젝트/          ← 이게 저장소 (레포)
├── index.html
├── style.css
├── README.md
└── .git/            ← Git이 변경 기록을 보관하는 곳 (숨김 폴더)
```

---

### 2. 커밋 (Commit)

> **비유: 게임 세이브 포인트**

롤플레잉 게임에서 보스 앞에 서면 먼저 세이브하잖아요? 커밋도 똑같습니다. "지금 이 상태를 저장해둘게" 하는 거예요.

```
커밋 1: "홈페이지 뼈대 만듦"        ← 세이브 포인트 1
커밋 2: "색깔이랑 글꼴 입힘"        ← 세이브 포인트 2
커밋 3: "연락처 페이지 추가"        ← 세이브 포인트 3
커밋 4: "뭔가 잘못됨 😱"           ← 여기서 실수!
         ↓
      커밋 3으로 되돌리기!          ← 세이브 로드!
```

클로드에게 이렇게 말하면 됩니다:

```
"지금까지 한 거 커밋해줘"
```

---

### 3. 푸시 (Push)

> **비유: USB에 있던 파일을 네이버 클라우드에 올리기**

커밋은 **내 컴퓨터에만** 저장됩니다. 이걸 GitHub(클라우드)에 올리는 게 푸시입니다.

```
내 컴퓨터 (로컬)          GitHub (클라우드)
    📁 ──── push ────→     ☁️

"올린다" = push
```

왜 필요하냐고요?
- 컴퓨터가 고장 나도 **백업**이 있으니 안전합니다
- 다른 컴퓨터에서도 **같은 파일**을 받아올 수 있습니다

```
"깃허브에 푸시해줘"
```

---

### 4. 풀 (Pull)

> **비유: 네이버 클라우드에서 최신 파일 내려받기**

푸시의 반대입니다. GitHub에 있는 최신 버전을 내 컴퓨터로 가져오는 거예요.

```
내 컴퓨터 (로컬)          GitHub (클라우드)
    📁 ←── pull ──────     ☁️

"내려받는다" = pull
```

집 컴퓨터에서 작업하고 푸시한 뒤, 회사 컴퓨터에서 풀하면 이어서 작업할 수 있습니다.

---

### 5. 브랜치 (Branch)

> **비유: 복사한 레시피에 실험하기**

김치찌개 레시피를 완성했는데, "된장 넣으면 어떨까?" 싶을 때 — 원본은 놔두고 **복사본에서 실험**하잖아요?

```
원본 레시피 (main) ─────────────────→ 안전하게 유지
         │
         └── 실험 레시피 (된장 버전) ─→ 여기서 마음껏 실험
                    │
                    ├── 맛있다! → 원본에 합치기 ✅
                    └── 별로다… → 그냥 버리기 🗑️
```

이게 브랜치입니다. **원본을 건드리지 않고 안전하게 실험**하는 공간.

---

### 6. 머지 (Merge)

> **비유: 실험 레시피를 원본에 합치기**

브랜치에서 실험한 게 맘에 들면, 원본(main)에 합칩니다. 이걸 머지라고 합니다.

```
원본 (main):        김치찌개 기본
실험 (feature):     + 된장 1스푼 추가
                        ↓ merge
원본 (main):        김치찌개 기본 + 된장 1스푼   ← 합쳐짐!
```

---

### 7. PR (Pull Request, 풀 리퀘스트)

> **비유: "이렇게 바꿔도 될까요?" 하고 허락 받기**

혼자 작업하면 바로 머지하면 되지만, 팀으로 일할 때는 **"제가 이렇게 바꿨는데 괜찮은지 봐주세요"** 하고 요청합니다. 이게 PR입니다.

```
나: "로그인 기능 만들었어요. 확인해주세요!" (PR 생성)
        ↓
팀장: "코드 봤어요. 여기 한 군데만 고치면 완벽!" (리뷰)
        ↓
나: "수정했습니다!" (수정 커밋)
        ↓
팀장: "좋아요, 합칩시다!" (머지 승인)
```

클로드에게는 이렇게 말하면 됩니다:

```
"PR 만들어줘"
```

그러면 클로드가 알아서 제목, 설명, 변경 내용 요약까지 작성해서 GitHub에 올려줍니다.

---

### 8. 클론 (Clone)

> **비유: 친구 레시피 노트를 통째로 복사하기**

GitHub에 있는 프로젝트를 **내 컴퓨터에 그대로 복사**해오는 것입니다.

```bash
git clone https://github.com/친구/맛있는-레시피.git
```

이러면 `맛있는-레시피` 폴더가 내 컴퓨터에 생기고, 모든 파일 + 모든 변경 기록까지 통째로 옵니다.

---

### 9. 스테이징 (Staging, "Add")

> **비유: 택배 보내기 전에 박스에 담기**

커밋하기 전에, **어떤 파일을 저장할지 골라서 담는** 과정입니다.

```
변경된 파일들:
  ✏️ index.html      ← 이건 보낼 거 (박스에 담음)
  ✏️ style.css       ← 이것도 보낼 거 (박스에 담음)
  ✏️ 메모.txt        ← 이건 아직 안 보낼 거 (빼둠)

git add index.html style.css   ← 박스에 담기 (스테이징)
git commit                     ← 택배 보내기 (커밋)
```

클로드가 커밋할 때 자동으로 필요한 파일만 골라서 담아줍니다.

---

### 10. 충돌 (Conflict)

> **비유: 두 사람이 같은 레시피의 같은 줄을 동시에 고친 상황**

```
나:   "고춧가루 2큰술"로 수정
동료: "고춧가루 3큰술"로 수정
         ↓
    충돌 발생! "도대체 몇 큰술이야?"
```

Git이 "여기 두 사람이 다르게 고쳤는데, 어느 쪽을 쓸 거야?" 하고 물어봅니다. 클로드에게 "충돌 해결해줘"라고 하면 양쪽을 비교해서 해결해줍니다.

---

## 전체 흐름 — 한 장으로 보기

```
① 작업하기
   코드를 수정하거나 파일을 추가합니다
        ↓
② 스테이징 (add)
   "이 파일들을 저장할 거야" 선택합니다
        ↓
③ 커밋 (commit)
   "지금 상태를 세이브!" 기록합니다
        ↓
④ 푸시 (push)
   GitHub 클라우드에 올립니다
        ↓
⑤ (팀 작업 시) PR 생성
   "이렇게 바꿔도 될까요?" 요청합니다
        ↓
⑥ 머지 (merge)
   승인되면 원본에 합칩니다
```

## 클로드 코드에서는 이 모든 게 쉬워집니다

Git 명령어를 외울 필요가 없습니다. 한국어로 말하면 클로드가 알아서 합니다.

| 하고 싶은 것 | 클로드에게 이렇게 말하세요 |
|------------|----------------------|
| 세이브하고 싶다 | "지금까지 한 거 커밋해줘" |
| 클라우드에 올리고 싶다 | "깃허브에 푸시해줘" |
| 최신 버전 받고 싶다 | "풀 받아줘" |
| 실험 공간 만들고 싶다 | "새 브랜치 만들어줘" |
| 실험 결과 합치고 싶다 | "main에 머지해줘" |
| 팀에 검토 요청하고 싶다 | "PR 만들어줘" |
| 뭐가 바뀌었는지 보고 싶다 | "변경사항 보여줘" |
| 이전 버전으로 돌리고 싶다 | "마지막 커밋 전으로 돌려줘" |
| 프로젝트 복사해오고 싶다 | "이 레포 클론해줘" |

> **핵심**: Git은 도구일 뿐이고, **클로드가 대신 다뤄줍니다.** 여러분은 "뭘 하고 싶은지"만 말하면 됩니다.

## GitHub은 뭐가 다른 건가요?

혼동하기 쉬운데, **Git ≠ GitHub**입니다.

| | Git | GitHub |
|---|---|---|
| **정체** | 프로그램 (도구) | 웹사이트 (서비스) |
| **비유** | 카메라 | 사진 클라우드 (Google Photos) |
| **역할** | 내 컴퓨터에서 버전 기록 | 그 기록을 인터넷에 보관 |
| **비용** | 무료 | 무료 (유료 기능 있음) |
| **필수?** | Git만 써도 됨 | 백업/협업하려면 필요 |

카메라(Git)로 사진을 찍고, Google Photos(GitHub)에 올려서 백업하고 공유하는 것과 같습니다.

## 자주 나오는 질문

### "나는 개발자가 아닌데 Git을 왜 알아야 해요?"

클로드 코드로 웹사이트를 만들거나, 자동화 스크립트를 짜면 그 결과물이 **파일**로 생깁니다. Git은 그 파일들을 안전하게 관리하고, 실수해도 되돌릴 수 있게 해주는 **안전망**입니다.

### "GitHub 계정이 꼭 필요한가요?"

로컬에서 Git만 써도 버전 관리는 됩니다. 하지만 **백업, 다른 PC 동기화, Vercel 배포** 등을 하려면 GitHub 계정이 필요합니다. 무료로 만들 수 있어요.

### "실수로 중요한 파일을 지워도 복구되나요?"

커밋해둔 상태라면 **언제든 복구**할 수 있습니다. 그래서 자주 커밋하는 습관이 중요합니다. 게임에서 자주 세이브하는 것과 똑같은 이치예요.

### "private 저장소는 남들이 못 보나요?"

네. private(비공개) 저장소는 **나만** 볼 수 있습니다. 공개하고 싶은 프로젝트만 public으로 만들면 됩니다.
