## 다이나믹 워크플로우가 뭔가요?

**Dynamic Workflows**(다이나믹 워크플로우)는 "클로드가 계획을 짜고, 그 계획대로 여러 클로드를 시켜서 일을 나눠 처리하게 하는" 방식이에요.

기존의 서브에이전트(subagent)와 차이점:

| 방식 | 내가 해야 하는 일 | 규모 |
|---|---|---|
| **일반 서브에이전트** | 어떤 에이전트를 만들지 직접 설계 | 소규모 |
| **다이나믹 워크플로우** | 목표만 말하면 클로드가 알아서 스크립트 작성 + 실행 | **대규모** |

> 🍱 **비유**: 큰 건물을 지을 때, 건축가(메인 클로드)가 설계도를 그리고, 그 설계도대로 전기팀·배관팀·인테리어팀(서브에이전트들)에게 각각의 일을 나눠주는 것. 건축가가 직접 공구 들고 일하지 않아요 — 지휘만 해요.

---

## 언제 쓰면 좋을까요?

공식 문서에서 권장하는 사용 사례:

### ✅ 코드베이스 전체 감사(Codebase Audit)

"우리 코드에서 deprecated API를 모두 찾아줘"처럼 **전체 코드를 쭉 훑어야 하는 작업**.

혼자 하면 파일 수천 개를 순서대로 봐야 하지만, 다이나믹 워크플로우를 쓰면 100개씩 묶어서 100개의 에이전트가 동시에 처리할 수 있어요.

### ✅ 대형 마이그레이션(Large Migration)

"Python 2 코드를 Python 3로 바꿔줘" 또는 "이 API 호출 방식을 전부 새 버전으로 교체해줘" 같은 **규모가 큰 일괄 변환**.

### ✅ 교차 검증 리서치(Cross-Checked Research)

"이 10개 논문에서 공통된 결론을 뽑아줘" 처럼 **여러 소스를 동시에 분석해서 결과를 비교하는 작업**.

---

## 어떻게 사용하나요?

### 기본 사용법

```bash
claude "우리 코드베이스 전체에서 하드코딩된 API 키를 찾아서 목록 만들어줘"
```

이렇게 말하면, 클로드가 알아서:
1. 코드베이스 구조 파악
2. 스캔 전략 수립 (어떤 파일 타입을 볼지, 몇 개씩 묶을지)
3. 서브에이전트 스크립트 자동 작성
4. 실행 + 결과 취합
5. 최종 보고서 제출

### 스크립트 재사용

클로드가 작성한 워크플로우 스크립트는 저장해뒀다가 **재사용**할 수 있어요:

```bash
# 워크플로우 스크립트가 .claude/workflows/api-key-scan.md 에 저장됐다면
/run api-key-scan
```

> 🍱 **비유**: 처음엔 건축가에게 설계도를 새로 그려달라고 하지만, 비슷한 건물을 또 지을 땐 기존 설계도를 재활용하는 것처럼요.

## 일반 서브에이전트 vs 다이나믹 워크플로우 비교

| 항목 | 일반 서브에이전트 | 다이나믹 워크플로우 |
|---|---|---|
| 설계 | 내가 직접 | **클로드가 자동 작성** |
| 적합한 규모 | 수 개 파일 | **수백~수천 파일** |
| 재사용 | 수동 | **스크립트 저장 후 재실행** |
| 진입 장벽 | 설계 지식 필요 | **목표만 말하면 됨** |
| 결과 검증 | 개별 확인 | **교차 검증 자동화 가능** |

---

## 실전 예시 프롬프트

```
"이 레포의 모든 .py 파일에서 try-except가 너무 넓게 쓰인 곳(except Exception: pass 패턴)을 
전부 찾아서, 파일명·줄번호·코드 스니펫 목록을 만들어줘.
파일이 많으니까 병렬로 처리해서 빠르게 해줘."
```

클로드는 이 지시를 받아:
- 파일을 N개 묶음으로 나눔
- 각 묶음을 서브에이전트에게 할당
- 결과를 취합해서 전체 목록 반환

---

## 주의사항

- 서브에이전트 수가 많아질수록 **토큰(비용)**도 그만큼 늘어요. 큰 규모 작업은 비용 먼저 확인하세요.
- 동시에 너무 많은 파일을 수정하는 작업은 **충돌 가능성**이 있으니 리드-온리(읽기 전용) 분석부터 하는 게 안전해요.
- 자동 생성된 스크립트는 실행 전에 한 번 검토하는 습관을 들이세요.
