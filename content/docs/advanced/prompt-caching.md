## 프롬프트 캐싱이란?

Claude Code는 대화를 할 때마다 매번 **전체 대화 내용을 API에 다시 보내야** 해요. 10번 대화했으면 10번 모두 처음부터 다시 보내는 거예요. 이게 비효율적이니까, **이미 처리한 부분은 저장해뒀다가 재사용**하는 게 바로 **프롬프트 캐싱(Prompt Caching)** 이에요.

> 🍜 **비유로 설명하면**: 라면 끓이는 레시피를 매번 처음부터 읽는 대신, "라면 끓이는 법"은 이미 외워뒀고 오늘 재료만 새로 확인하는 것처럼요. 이미 아는 부분(캐시)은 건너뛰고 새 내용만 처리해요.

**Claude Code가 자동으로 관리**하니까 별도 설정 없이도 캐싱은 작동해요. 하지만 **어떤 행동이 캐시를 깨뜨리는지** 알면, 느리고 비싼 순간을 피할 수 있어요.

---

## 캐시 3단계 구조

Claude Code는 요청을 보낼 때 변하지 않는 것부터 먼저 쌓아요:

| 계층 | 내용 | 언제 바뀌나요? |
|---|---|---|
| **1. 시스템 프롬프트** | 기본 지시사항, 도구 정의 | MCP 서버 연결/해제 시, Claude Code 업데이트 시 |
| **2. 프로젝트 컨텍스트** | CLAUDE.md, 메모리, 규칙 파일 | 세션 시작 시, /clear·/compact 이후 |
| **3. 대화 내용** | 내 메시지, Claude 답변, 도구 결과 | 매 턴마다 추가됨 |

아래 계층이 바뀌어도 위 계층은 캐시가 유지돼요. 하지만 **위 계층이 바뀌면 그 아래 모든 것도 캐시가 깨져요**.

> 🏗️ **비유**: 아파트 1층이 무너지면 2층·3층도 같이 무너지는 것처럼요.

## 캐시가 깨지는 행동들 (비용·속도 주의!)

이런 행동을 하면 다음 요청이 **한 번 느리고 비싸게** 처리돼요 (그 이후엔 다시 캐시 재구축):

### 1. 🔄 모델 전환

```bash
> /model claude-opus-4-7    # 전환 직후 첫 응답 = 캐시 미스!
```

각 모델은 자신만의 캐시를 갖고 있어요. 모델을 바꾸면 내용이 똑같아도 처음부터 다시 처리해요.

> ⚠️ 특히 `opusplan` 설정: 플랜 모드에서 Opus, 실행 모드에서 Sonnet을 쓰도록 설정하면, **플랜 모드 ↔ 실행 모드 전환할 때마다** 모델이 바뀌어서 캐시가 깨져요.

### 2. 🔌 MCP 서버 연결/해제

MCP(엠씨피) 도구 목록은 시스템 프롬프트에 포함돼요. MCP 서버가 연결되거나 끊기면 1계층이 바뀌어서 전체 캐시가 깨져요.

이런 상황에서 자동으로 끊길 수 있어요:
- stdio 서버 프로세스가 종료될 때
- HTTP 세션 만료 시
- 서버 자동 재연결 시

### 3. 🚫 도구 전체 차단

```bash
> /permissions      # Bash 전체를 deny(거부)로 설정하면
```

`Bash`나 `WebFetch` 같은 도구를 **완전히** 차단하면 시스템 프롬프트에서 그 도구 정의가 빠져서 캐시가 깨져요. 반면 `Bash(rm *)` 같은 **세부 제한**은 캐시에 영향 없어요.

### 4. 📦 /compact (대화 압축)

```bash
> /compact
```

대화 내용을 요약으로 교체하니까 3계층이 바뀌고, 캐시가 재구축돼요. (단, 요약 생성 자체는 기존 캐시를 활용해서 효율적으로 처리해요)

### 5. ⬆️ Claude Code 업그레이드

새 버전이 설치되면 시스템 프롬프트도 바뀌어서 첫 시작 시 전체 재처리해요. 자동 업데이트는 백그라운드에서 다운로드 후 **다음 실행 시** 적용되니까, 세션 중간에 갑자기 느려지지 않아요.

## 캐시가 유지되는 행동들 (안심!)

이런 건 해도 캐시가 깨지지 않아요:

| 행동 | 이유 |
|---|---|
| 파일 수정 | Claude가 읽을 때 대화에 추가될 뿐, 이전 내용은 그대로 |
| **세션 중 CLAUDE.md 수정** | 세션 시작 시 이미 읽었으므로 캐시 유지 (변경도 미적용!) |
| 출력 스타일 변경 (`/config`) | 다음 세션 시작 시에 반영 (현재 세션엔 미적용) |
| 권한 모드 전환 | 모델/도구 변화 없음 |
| 스킬·명령어 실행 | 대화 끝에 추가될 뿐 |
| /recap | 요약을 대화에 추가만 할 뿐, 기존 내역 유지 |
| /rewind (되감기) | 이전 시점으로 돌아가면 그 시점 캐시 그대로 |

> 💡 **팁**: CLAUDE.md를 세션 중에 고쳤는데 적용이 안 된다면? 정상이에요. `/clear` 또는 세션 재시작 후 적용돼요.

## 캐시 유지 시간 (TTL)

캐시는 일정 시간 동안만 보존돼요. 요청이 있을 때마다 시간이 초기화돼요.

| 상황 | 기본 TTL | 변경 방법 |
|---|---|---|
| **Claude 구독 플랜** (Pro, Max) | **1시간 자동** | 무료라 기본 적용 |
| API 키 / AWS Bedrock / Google Vertex | 5분 | `ENABLE_PROMPT_CACHING_1H=1`로 1시간 전환 |
| 구독 사용량 초과 후 사용 크레딧 소진 시 | 5분으로 자동 전환 | |

```bash
# 5분으로 강제 고정 (테스트·디버그용)
export FORCE_PROMPT_CACHING_5M=1

# 1시간으로 전환 (API 키 사용자)
export ENABLE_PROMPT_CACHING_1H=1
```

## 캐시 성능 확인하기

**statusline(상태바)**를 설정하면 캐시 히트율을 실시간으로 볼 수 있어요.

| 항목 | 의미 |
|---|---|
| `cache_read_input_tokens` | 캐시에서 읽은 토큰 수 (약 10% 비용) |
| `cache_creation_input_tokens` | 이번 턴에 새로 캐시에 쓴 토큰 수 (100% 비용) |

> ✅ **read가 높고, creation이 낮을수록** 캐시가 잘 작동하는 것

creation이 매 턴 계속 높다면 → 위의 "캐시가 깨지는 행동" 목록에서 원인을 찾아보세요.

## 서브에이전트(Subagent)와 캐시

서브에이전트(하위 AI 작업)는 **부모 대화와 별개의 캐시**를 가져요. 처음 호출 시엔 항상 캐시 미스이고, 이후 자기 턴을 거치며 자체 캐시를 만들어요.

단, **fork(포크, 대화 복제)**는 부모의 시스템 프롬프트·대화를 그대로 복사해서 부모 캐시를 바로 활용해요.

---

## 캐싱 비활성화 (테스트·디버그용)

```bash
# 전체 비활성화
export DISABLE_PROMPT_CACHING=1

# 특정 모델만
export DISABLE_PROMPT_CACHING_HAIKU=1
export DISABLE_PROMPT_CACHING_SONNET=1
export DISABLE_PROMPT_CACHING_OPUS=1
```

> ⚠️ 일반 사용에서는 캐싱을 끄면 비용이 크게 올라가요. 문제 진단할 때만 사용하세요.

## 💡 캐시 효율 높이는 실전 팁

```
✅ 세션 시작할 때 모델·MCP 서버 먼저 설정하고 변경하지 않기
✅ /compact는 작업 전환 타이밍에 (중간엔 피하기)
✅ 되돌리고 싶으면 /compact보다 /rewind 활용
✅ 모델 자주 바꾸지 않기 (특히 opusplan 설정 주의)
```
