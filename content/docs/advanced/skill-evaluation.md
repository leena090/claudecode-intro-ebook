## 스킬 평가가 왜 필요한가요?

스킬(SKILL.md)을 만들어서 쓰다 보면 이런 고민이 생겨요:

- "이 스킬 진짜 잘 작동하는 거 맞아?"
- "어제 바꾼 프롬프트가 더 나아진 건가, 오히려 망친 건가?"
- "스킬 A랑 B 중에 어느 게 더 정확해?"

이런 질문에 **감이 아닌 데이터로** 답하는 게 **스킬 평가(Skill Evaluation, 줄여서 eval)**예요.

> 🍱 **비유로 설명하면**: 김치 담글 때 "이번 김치 맛있나?" 물어볼 때, 가족 한 명한테만 물어보면 부정확해요. 10명한테 **똑같은 조건**에서 맛보게 하고 점수 매겨야 진짜 평가가 돼요. 스킬도 마찬가지입니다.

---

## 언제 eval을 해야 하나요?

| 상황 | 왜 |
|---|---|
| 🆕 **스킬 처음 배포 전** | 내 컴퓨터에서만 되는 건지, 실제 다양한 입력에도 잘 되는지 |
| ✏️ **스킬 수정 후** | 수정이 개선인지, 개악인지 |
| 🐛 **갑자기 이상해졌을 때** | 뭐가 틀어졌는지 원인 추적 |
| ⚖️ **스킬 A vs B 선택** | A/B 테스트로 객관 비교 |
| 🔄 **Claude 모델 업그레이드 후** | Opus 4.6 → 4.7 같은 버전 변경 시 기존 스킬이 여전히 잘 되는지 |

## 🧪 eval 3단계 — 가장 간단한 방법

### 1단계: **입력 샘플 10개** 준비

실제로 스킬을 쓸 때 들어올 만한 입력 10개를 다양하게 모으세요. 많지 않아도 돼요. **"보통 / 까다로운 / 이상한"** 3종류가 골고루 있으면 OK.

**예시**: 블로그 글 작성 스킬 `/blog`의 평가 샘플

```
1. "AI 자동화로 하루 1시간 아끼는 법"        ← 보통
2. "50대 엄마가 유튜브 시작하는 법"            ← 보통
3. "비트코인 반감기 쉽게 설명"                  ← 까다로움 (기술 주제)
4. "우리 강아지가 귀여운 이유 10가지"          ← 이상함 (비업무)
5. "주식 초보를 위한 종목 추천"                ← 까다로움 (투자 조언)
...
```

### 2단계: **기대 출력 기준** 정하기

각 샘플에 대해 "이 정도면 합격" 기준을 **미리** 적어두세요. 나중에 결과 보고 정하면 편향이 생겨요.

| 샘플 번호 | 합격 기준 (체크리스트) |
|---|---|
| 1 | ✅ 제목에 키워드 / ✅ 2,000자 이상 / ✅ H2 3개 이상 / ✅ 예시 2개 이상 |
| 2 | ✅ 40~60대 톤 / ✅ 비유 1개 이상 / ✅ 장비 추천 포함 |
| 3 | ✅ 전문용어 → 일상어 풀이 / ✅ 비유 2개 이상 |

### 3단계: **스킬 실행 → 체크리스트 확인**

각 샘플에 대해 스킬을 돌리고 체크리스트 개수를 세요.

```
샘플 1: 5개 중 5개 ✅   (100%)
샘플 2: 3개 중 3개 ✅   (100%)
샘플 3: 4개 중 2개 ❌   (50%)  ← 여기 문제!
...
```

**통과 기준**: 10개 샘플 평균 **80% 이상**이면 배포 OK. 그 이하면 수정 후 재측정.

## ⚖️ A/B 테스트 — 두 스킬 비교

"스킬 v1"과 "스킬 v2" 중 어느 게 더 나은지 비교할 때 씁니다.

### 절차

1. **똑같은 샘플 10개**를 두 스킬에 동일하게 돌리기
2. 각 결과를 **같은 체크리스트**로 채점
3. 평균 점수 비교

**예시 결과**

| 샘플 | 스킬 v1 | 스킬 v2 |
|---|---|---|
| 1 | 80% | **100%** |
| 2 | 100% | 80% |
| 3 | 60% | **80%** |
| 4 | 100% | 100% |
| 5 | 40% | **60%** |
| ... | ... | ... |
| **평균** | **76%** | **84%** ✅ |

→ **스킬 v2 승리**. 다만 샘플 2처럼 v1이 더 나은 경우도 있으니 **"어떤 타입에서 왜 다른지"** 분석도 하세요.

### ⚠️ A/B 테스트 주의사항

- **같은 조건**에서 돌리기 — 다른 날, 다른 모델, 다른 컨텍스트면 비교 의미 없음
- **최소 10개 샘플** — 5개 이하는 우연일 수 있음
- **체크리스트를 먼저 만들기** — 결과 보고 기준 정하지 말기

> 🍱 **비유로 설명하면**: 두 식당 비교 리뷰할 때 "A는 점심에 가고 B는 저녁에 갔다"면 공정한 비교가 안 돼요. 같은 시간·같은 메뉴로 가야 진짜 비교입니다.

## 💰 eval 시 체크할 3가지 지표

단순히 "잘 작동하나?"만 보지 말고 **3가지 지표**를 같이 보세요.

| 지표 | 뭘 보나 | 예시 |
|---|---|---|
| **정확도** | 원하는 결과가 나왔나? | 체크리스트 통과율 |
| **속도** | 얼마나 걸렸나? | 평균 응답 시간 |
| **토큰 비용** | 얼마나 썼나? | 샘플당 평균 토큰 |

**실제 선택 시나리오**

| | 스킬 v1 | 스킬 v2 | 판단 |
|---|---|---|---|
| 정확도 | 76% | 84% | v2 ↑ |
| 속도 | 5초 | 12초 | v1 ↑ |
| 토큰 | 2,000 | 8,000 | v1 ↑ |

→ v2가 정확도는 높지만 **토큰 4배**. 하루 100번 쓰는 스킬이면 v1이 유리할 수도 있어요. **목적에 따라 다른 답**이 나옵니다.

## 🛠️ 간단한 eval 스크립트 (Node.js)

커뮤니티에서 많이 쓰는 방식 — 자동화된 배치 평가 스크립트입니다.

**Mac 터미널 / Windows PowerShell**

```javascript
// eval-blog-skill.mjs
import { readFileSync } from 'fs';
import Anthropic from '@anthropic-ai/sdk';

const client = new Anthropic();
const samples = JSON.parse(readFileSync('./eval-samples.json', 'utf-8'));

let totalScore = 0;
for (const sample of samples) {
  const response = await client.messages.create({
    model: 'claude-sonnet-4-6',
    max_tokens: 4000,
    messages: [{ role: 'user', content: `/blog ${sample.input}` }]
  });

  const output = response.content[0].text;
  const score = checkCriteria(output, sample.criteria);
  totalScore += score;

  console.log(`샘플 ${sample.id}: ${score}% ${score >= 80 ? '✅' : '❌'}`);
}

console.log(`\n평균: ${totalScore / samples.length}%`);

function checkCriteria(output, criteria) {
  // 체크리스트 항목별 검사 — 간단한 정규식 또는 LLM으로 판정
  const passed = criteria.filter(c => output.includes(c)).length;
  return (passed / criteria.length) * 100;
}
```

<div class="note-circle">
○ 이 스크립트는 <strong>예시</strong>일 뿐이에요. 실제로는 <code>/claude-api</code> 빌트인 스킬이 상세 가이드를 제공합니다.
○ 더 정교한 평가가 필요하면 <strong>LLM as Judge</strong>(Claude가 결과를 채점하는 방식)도 있어요.
</div>

## 🧠 LLM as Judge — Claude에게 채점 맡기기

체크리스트 대신 **Claude가 결과를 평가**하게 하는 방법입니다.

```
다음 블로그 글이 아래 기준을 얼마나 충족하는지 1~10점으로 채점해줘:

기준:
1. 40~60대 타겟 톤 (친근함)
2. 일상 비유 포함
3. 2,000자 이상
4. H2 제목 3개 이상

채점할 글:
---
{스킬이 만들어낸 블로그 글}
---

출력 형식: JSON
{
  "tone_score": N,
  "metaphor_score": N,
  "length_score": N,
  "structure_score": N,
  "total_score": N,
  "feedback": "개선할 점"
}
```

**장점**:
- 정규식보다 미묘한 품질 차이를 잘 잡아냄
- 피드백까지 받음

**단점**:
- Claude API 비용 추가 발생
- 평가자 Claude의 편향 가능성

## ⚠️ 함정 & 실패 케이스 수집

eval 하다 보면 **실패 케이스**가 나옵니다. 이걸 그냥 넘기지 말고 **모아두세요**.

### 실패 케이스 파일 예시

```markdown
# /blog 스킬 실패 케이스

## 2026-04-08
- 입력: "비트코인 반감기 쉽게 설명"
- 문제: 전문용어(hash, mining)를 풀어쓰지 않음
- 기대: "채굴 = 금 캐는 것과 비슷" 같은 비유
- 조치: SKILL.md에 "전문용어는 반드시 일상 비유로 풀이" 추가

## 2026-04-07
- 입력: "50대 엄마 유튜브 시작"
- 문제: 장비 추천이 너무 전문적 (소니 A7IV 등)
- 기대: 스마트폰부터 시작하는 현실적 순서
- 조치: "초보자 장비 우선" 원칙 추가
```

이 파일이 쌓이면 **스킬 v2의 개선 방향**이 자연스럽게 나와요.

## 🎯 실전 요약 — 이것만 기억하세요

### ✅ 해야 할 것
1. **스킬 배포 전 10개 샘플 테스트**
2. **체크리스트를 먼저** 만들고 채점
3. **정확도 + 속도 + 토큰** 3가지 지표 함께 보기
4. **실패 케이스는 파일로 모으기**
5. **수정 후에는 반드시 재측정**

### ❌ 하지 말 것
1. 1~2개 결과만 보고 "잘 되네" 판단
2. 결과 보고 나서 기준 정하기 (편향 발생)
3. 주관적 "느낌"으로만 판단
4. 수정 후 재측정 안 하기

---

## 💡 초보자 팁 — 처음부터 완벽할 필요 없어요

처음 만든 스킬은 **70% 정확도**면 충분해요. 실제 사용하면서 실패 케이스가 쌓이고, 그걸 바탕으로 고치면 **90% → 95%** 점점 좋아집니다.

> 🍱 **비유로 설명하면**: 요리사도 처음부터 미쉐린 셰프가 되진 않아요. 만들고, 손님 반응 보고, 다시 만들고를 반복하며 실력이 늘어요. 스킬도 똑같아요.
